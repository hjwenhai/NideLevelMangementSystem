# SQLite可靠性与容量评估

## 状态

SQLite已由用户选定，128罐、默认60秒、保留一年及Windows10/11基线见ADR-003。配置/审计库已有实测，实际SQLite3.53.4、WAL/FULL、事务回滚及备份重开通过；全年历史容量仍待执行。下文保留此前评估依据，不能读为全年已验收。

## 背景

用户关注全年大量历史数据的可靠性。上个项目已有独立合成数据集验证，但新系统增加计量、质量、快照和事件内容，应独立验证。

## 判断

SQLite具备事务与崩溃恢复能力，数千万条本身不构成不可使用的理由。默认60秒归档时，现行128罐平均约2.13条/秒；历史索引、查询、备份与恢复成本比平均写入速度更需要验证。此判断不等于新系统已通过压力或故障测试。

当前单主机、服务端统一访问和分钟级归档方案可继续选择SQLite为本期数据库。最大罐数和最短归档周期应确定为设计负载。若需秒级长期全量历史、多进程并发写入或大范围统计超出目标响应，优先评估PostgreSQL；应在完整业务开发前完成容量验证。

## 可靠性设计

- 数据库存本地磁盘，其他电脑只访问后台接口；后台统一管理写入，任务控制审计通过持久化事务先记录再发送。
- 采用包含已知WAL-reset修复的原生SQLite版本，核对运行时实际sqlite_version；依赖更新后回归。
- WAL配合synchronous=FULL，事务批量提交。区分已提交数据、尚在内存的采样和设备未产生的数据，不承诺物理硬盘故障零丢失。
- 写入队列有界并监测等待、失败和积压；磁盘不足或数据库保存失败明确告警，不显示为保存成功。新控制的审计前提与停止处理路径分别设计。
- 历史按罐ID与采集时间索引；查询分页，导出分批，限制长读事务和WAL膨胀。完整配置和罐容表按版本保存，历史引用，不逐条保存全量配置。
- 默认60秒历史归档与实时采集、推送分开；任务、报警、操作和重要质量变化保留相应完整记录，另估算容量。
- 采用在线一致性备份并定期验证实际恢复；备份放独立介质或内部备份位置，记录可恢复到的时点。保留数据库/WAL必要恢复文件，不能只复制正在运行的主db文件。
- 数据完整性检查、空间预警、恢复预演纳入维护。是否按月归档/分库在压测后决定；分库不是自动提高事务可靠性的保证，须处理跨库查询、配置版本及一致性备份。

## 必须完成的验证

以目标最大罐数和最短历史周期生成完整一年真实字段与索引的合成数据，同时做持续采集、常用历史及曲线、全罐查询、长范围Excel、备份和已备份文件实际恢复。记录耗时、峰值内存、库/WAL大小、采集延迟和等待情况。加入进程强制退出、重启、磁盘写入失败等隔离测试；真实断电和目标电脑环境另做现场验证。

验收门槛与目标硬件结合确定，不能只凭条数或理论最大容量承诺响应。若优化后的SQLite仍不满足门槛，在正式铺开前改用PostgreSQL。
