## 4 设备校验和首次安装

新机安装后先在“系统维护→设备永久授权”下载申请、导入厂家文件，再人工重启程序并检查采集。客户的 0.6.0 ARM64 样机可在网页安装 0.7.0-20261109-r2 过渡包，下载申请并导入厂家授权，再安装 0.8.1。两次安装步骤和现场复核项目见[网页升级说明](29_网页上传升级操作说明.md)。厂家终端预授权见说明33第3节。

### 4.0 推荐：交互式向导

包当前为16个必要文件，向导已集成在install.sh中，不需要Python、Node或额外安装工具。上传新包后，在设备SSH或Console终端逐条执行；每条成功再继续。已有相同release不重复安装，向导不会覆盖它。

~~~sh
# 计算压缩包摘要，与第3节公布的SHA256核对。
sha256sum /tmp/gt6757s-0.8.3-20261117-r1-linux-arm64.tar.gz

# 解压已核对的新包。
tar -xzf /tmp/gt6757s-0.8.3-20261117-r1-linux-arm64.tar.gz -C /tmp

# 启动交互式安装向导，程序会自动区分首次安装和升级。
sh /tmp/gt6757s-0.8.3-20261117-r1-linux-arm64/deploy/install.sh --guided /tmp/gt6757s-0.8.3-20261117-r1-linux-arm64
~~~

新机依次填写网页IP:端口、Modbus TCP IP:端口、实际已接台数、单台站址、波特率及校时许可；IP必须是设备已有IP，向导不修改Linux网卡。默认1台，南向8E1；多台按每口16台和站址1～16生成，可在网页调整。所有真实控制默认关闭；新机先核对SYS灯占用，本台驱动已确认，升级保留现有LEDS值。确认后自动生成配置、安装、设置网页管理员密码、启动及检查core。密码输入不回显，重复输入不一致时重试。

升级自动保留原账号、应用配置及现有启动参数；缺失的支持参数从新模板补齐，原值不改。安装器先验证包和配置，备份数据和启动配置，新core健康失败时按原有兼容规则回退。向导不自动启用开机自启，也不代替现场采集/RTC/动作验收，自启按第8节办理。

向导成功后转第6、7节检查网页和采集；已允许校时时再按[说明23](23_时钟校核与断电恢复.md)校核一次。若不用向导，以下保留完整手动步骤。

### 4.3 手动安装：设置服务启动参数

用设备文本编辑器修改/home/level-gateway/config/service.env。以下是文件内容，不是直接输入终端就永久生效的命令。

~~~sh
# 设置网页端口；新版项目服务在两个IPv4网口监听，不改变网卡IP。
WEB_LISTEN=192.168.0.230:8088

# 首次只读采集，真实控制保持关闭。
HARDWARE_WRITES=0

# 首次不允许网页修改系统时钟。
ALLOW_CLOCK_SET=0

# RTC统一保存UTC；如实机节点不同，先确认后修改此路径。
RTC_DEVICE=/dev/rtc0

# 看门狗未经专门验证前留空。
WATCHDOG=

# HTTPS证书路径，不启用HTTPS时留空。
TLS_CERT=

# 配套私钥路径，与证书同时配置或同时留空。
TLS_KEY=

# 确认原厂占灯服务及唯一控制方前，先关闭实体SYS灯驱动。
LEDS=0
~~~

文件使用LF换行，等号两边不加空格。修改后按实际服务管理方式重启生效。

## 5 创建管理员并启动

**设备终端执行。网页账号与Linux root账号分别管理。**

本步骤分开执行，每次只复制当前代码块。初始化程序没有密码提示语；执行后光标停住时，就是在等待输入密码。不要把后续查询或启动命令一同粘贴。

先隐藏输入：

~~~sh
# 暂时关闭终端输入回显。
stty -echo
~~~

再单独执行初始化命令：

~~~sh
# 运行后输入自定的12～128个ASCII字符密码并按回车，输入时不显示字符。
/home/level-gateway/current/bin/gateway-web --init-admin --auth-file /home/level-gateway/data/admin.json
~~~

等它返回后，无论成功或失败，都先恢复回显。成功应显示“管理员凭据已初始化”。

~~~sh
# 恢复终端输入显示。
stty echo

# 确认凭据文件存在，不打印内容。
ls -l /home/level-gateway/data/admin.json
~~~

确认初始化成功后再启动服务：

~~~sh
# 启动采集核心和网页服务。
sh /home/level-gateway/current/deploy/service.sh start

# 查看两个监督器是否运行。
sh /home/level-gateway/current/deploy/service.sh status

# 检查核心调度，预期healthy。
/home/level-gateway/current/bin/gateway-core --health-check --ipc unix:/home/level-gateway/data/core.sock

# 查看采集核心最近60行日志。
tail -n 60 /home/level-gateway/logs/core.log

# 查看网页服务最近60行日志。
tail -n 60 /home/level-gateway/logs/web.log
~~~

已有admin.json时保留原凭据；日常改密码使用“系统维护→修改管理员密码”，原密码/新密码/再次确认后保存，所有网页会话退出，采集不中断。忘记密码由厂家在设备终端核查恢复，不删除数据库重建。详见[系统维护26第1节](26_系统维护与控制写入操作说明.md)。

## 6 网页和TCP检查

电脑浏览器访问http://192.168.0.230:8088。登录后“历史与诊断”应显示version=0.7.0、map_version=3、simulate=false，control_error为空。

**电脑PowerShell执行：**

~~~powershell
# 检查维护网页端口。
Test-NetConnection 192.168.0.230 -Port 8088

# 检查本次设备Modbus TCP端口。
Test-NetConnection 192.168.0.230 -Port 502
~~~

TCP连接成功还要实际读寄存器。电脑调试工具保留在电脑，按[说明22](22_电脑演示构建与客户资料管理.md)设置gatewayPython后：

~~~powershell
# 读取实体网关协议版本和容量，预期[3,64]。
& $gatewayPython ./tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 read 2 2

# 读取D2控制能力及步长，预期[3,12]。
& $gatewayPython ./tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 read 28 2

# 查看编号1数据摘要，工具自动换算单位并检查有效位。
& $gatewayPython ./tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 summary --meters 1

# 查询编号1控制状态，不提交动作。
& $gatewayPython ./tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 status --slot 1
~~~

本机演示为127.0.0.1:1502，实体设备本次为192.168.0.230:502，不能混用。

## 7 四个485口、采集和指示灯

### 7.1 COM配置

| 配置 | 用法 |
| --- | --- |
| 南向采集 | 网关为RTU主站，每口最多16台 |
| 北向RTU | 供上位机读取，同口不再挂液位计 |
| 停用 | 本应用不使用该口 |
| 南向参数 | 与仪表一致；FW为8E1、1200/2400/4800/9600，常用4800 |
| 超时 | 初次可500ms，随后按现场实测 |
| 仪表编号/站址 | 编号决定北向寄存器位置；站址是液位计自身地址 |

正常模式至少两路南向。首次只COM1接一台时，COM2可保留南向但不绑定仪表。同总线站址不重复，不同COM可相同；范围1～243。

| 配置规模 | COM1 | COM2 | COM3 | COM4 |
| --- | --- | --- | --- | --- |
| 32台＋RTU | 南向16 | 南向16 | 北向RTU | 停用 |
| 48台＋RTU | 南向16 | 南向16 | 南向16 | 北向RTU |
| 64台，仅TCP | 南向16 | 南向16 | 南向16 | 南向16 |

四口角色可置换。使用485的A/B端子，COM3/4的TX/RX是复用232，不能同时接两种接口。一条南向总线只由一个主站轮询。接线和四口逐一测试见[安装联调说明17](17_GT6757S安装与板端联调操作说明.md)。

### 7.2 常用网页参数

| 参数 | 建议起点及含义 |
| --- | --- |
| 正常/维护模式 | 正常采集；维护暂停南向轮询 |
| 快速周期3000ms | 常用数据采集目标，实际受台数、波特率和超时影响 |
| 详情周期30000ms | 启用的详情组采集目标；参数区另约10分钟 |
| TCP服务端口 | 实机默认502；端口与仪表只改端口，接入IP由系统维护所选网口确定。下方只读地址可复制；两个网口分别列出。 |
| TCP站号1 | 整个网关同一Unit ID，64台通过寄存器地址区分 |
| 并发连接8 | 同时客户端数，不是液位计数 |
| 允许TCP提交命令 | 首次关闭，读取不受影响 |
| 历史60秒/30天/256MiB | 保存快照间隔及保留策略，先达容量可能提前淘汰 |

网页“保存并应用配置”后回到当前数据核对。存在非空闲控制周期时有变更配置会被拒绝，先按D2处理原周期。

### 7.3 数据有效与采集验证

先单台对照液位计显示观察至少5分钟，再四口逐一、每口多台及满载。静止数值不变时通过年龄和成功组序号确认更新。

液位有效看valid与0x0001按位与非0，温度看0x0002，密度看0x0004；故障字另看有效位及实际值。默认有效窗口3000×3=9000ms，超过各组最后成功读取9秒才清相应位。

只读状态断一台通讯线但保留供电，验证告警、过期及重连恢复。记录掉线对同口其他仪表的影响，不用默认3秒代替实际刷新测量。

### 7.4 SYS灯

三个字符设备已确认存在，但仍要核对原厂是否有程序同时写灯。确认唯一控制方后将service.env设LEDS=1，再重启本应用。

| 灯 | 状态 |
| --- | --- |
| SYS1心跳 | core调度健康；不健康时常亮 |
| SYS2常亮/慢闪/快闪 | 快速数据全部正常/部分正常/没有一台全部正常 |
| SYS2灭 | 未授权、无启用仪表或维护模式 |
| SYS3慢闪 | 时间未确认或部分采集警告 |
| SYS3常亮 | 设备未授权、仪表故障、控制失败/未知、存储或驱动等严重异常 |
| SYS3灭 | 当前无告警 |

本台SYS实体驱动已由用户确认正确；其他故障场景仍可按实际触发记录灯态。TX/RX由串口硬件驱动，详细定义见[说明11](11_SYS状态指示灯.md)。

### 7.5 模拟量采集与查看（0.3.6）

1. 打开“端口与仪表”，在“仪表绑定”找到对应槽位，勾选“模拟量采集”。仪表本身也须启用。
2. 点击“保存并应用配置”。未保存的勾选不改变实际采集；存在未复位控制周期时，先按原流程处理该周期。
3. 打开“当前数据”，点击该液位计“查看”，在“模拟量 IR27～30”中检查四项数值、单位、原始字、网关零基地址及采集状态。
4. 取消勾选并保存即停止该仪表模拟量轮询，详情显示“未启用模拟量采集”和“—”。重新开启先等待读数，不沿用关闭前的值。

此开关只控制网关FC04读取，不修改液位计模拟量设置，也不发送浮子动作。首次默认关闭；升级保留已保存的meters[].analog值，不统一强制开启。程序重启保留开关，但缓存重新采集。成功/累计失败次数在本次程序运行内保留，开关切换不清零；这些运行计数不承诺跨程序重启保留。

模拟量按“详情周期”采集，默认30000ms（30秒），网页约每2秒刷新。实际更新受串口排队、仪表响应和重试影响，并非固定30秒保证。每启用一台，详情轮询增加一组IR27～30、共4字读取。满载现场应复测周期。

IR27、IR28是无符号原始字÷1000，单位mA；IR29、IR30先按int16解码再÷100，单位%。未启用或没有成功读数显示“—”；真正采集到0才显示0.000mA或0.00%。这些是仪表返回的模拟量输入和百分比，不由网关另行计算液位百分比。

详情单独显示未启用、等待首次采集、采集失败、寄存器不支持、维护暂停和过期等状态。已有值遇到失败/暂停/过期会标成旧值。模拟量网页参考窗口=3×已保存详情周期，默认3×30=90秒；数据年龄由网关单调时钟计算。窗口内一次失败仍可显示上次成功值，但必须同时保留警告；窗口外不作为当前有效值。时间未确认只说明日历时间未校核，不能单独据此判数值无效。

摘要有效字127只覆盖原快速字段，不包含模拟量。北向仍使用原详情区，仪表1读3027起4字；其它槽位及组状态见[点表15第9节](15_北向寄存器点表V3.md)。复制详情包含同一快照中的模拟量、单位和状态。

### 9.1 查看状态、日志和空间

~~~sh
# 查看current实际指向的release目录。
readlink /home/level-gateway/current

# 检查采集调度，预期healthy。
/home/level-gateway/current/bin/gateway-core --health-check --ipc unix:/home/level-gateway/data/core.sock

du -sh /home/level-gateway/data /home/level-gateway/logs
~~~

网页看在线数、年龄、valid/quality、control_error和灯态，不能只看进程存在。

历史CSV在“历史与诊断”导出：选择开始/结束时间，再在“液位计（槽位 / 名称）”选择目标，点击“导出CSV”。默认全部液位计，每次最多7天。保存快照不代表每次都新采到所有字段。近期事件最多5000条，API最多100条；长审计保留需厂家归档。

单台文件名为level-history-slot-01.csv等，全量仍为level-history.csv。原CSV前15列保持，末尾增加“液位计名称”“名称说明”。名称取导出时已保存配置，同槽位同绑定才填写；旧绑定或未配置记录留空并说明原因。更换仪表前后数据用槽位和绑定版本核对。CSV按槽位导出其各绑定版本历史，不会因当前停用或删除配置而丢弃历史；数据库已按保留策略淘汰的数据无法导出。名称以=、+、-、@等开头时按文本导出，前置单引号防止被表格软件解释为公式。

日志在监督器启动子进程前超过2MiB时轮转，持续运行时仍可能增长，需要定期查看空间。

### 9.2 数据库备份

SQLite使用WAL，不只拷贝运行中的.db文件。--backup-db只生成一致性快照，不启动采集、不迁移源库，目标不得存在。

~~~sh
# 生成本次备份UTC时间标签。
gateway_backup_stamp=$(date -u +%Y%m%dT%H%M%SZ)

# 创建仅当前用户可访问的新备份文件。
umask 077

# 创建维护备份目录。
mkdir -p /home/level-gateway/backups

# 生成包含已提交WAL的一致性库备份。
/home/level-gateway/current/bin/gateway-core --db /home/level-gateway/data/gateway-v2.db --backup-db "/home/level-gateway/backups/gateway-$gateway_backup_stamp.db"

# 同次保存实际应用配置。
cp /home/level-gateway/config/gateway.json "/home/level-gateway/backups/gateway-$gateway_backup_stamp.json"

# 同次保存服务启动配置。
cp /home/level-gateway/config/service.env "/home/level-gateway/backups/service-$gateway_backup_stamp.env"

# 已有校时记录时一并备份；恢复到另一台设备后必须重新校时。
if [ -f /home/level-gateway/data/clock-state.json ]; then cp /home/level-gateway/data/clock-state.json "/home/level-gateway/backups/clock-$gateway_backup_stamp.json"; fi
~~~

需要库与配置严格同一维护状态时先停服务。备份应再转存厂家电脑或受控存储，不在设备上无限累积。凭据和私钥另行私密保存，不放入普通回传资料。

### 9.3 时间、控制和看门狗

- 时间由校时记录及RTC开机检查自动确认，旧TIME_TRUSTED开关不再生效；未确认不妨碍按单调年龄判断数据有效。
- 允许网页校时及RTC保存时设ALLOW_CLOCK_SET=1并重启，先确认电脑时间。成功保存RTC及校时记录后，重启可自动检查恢复，详见[时钟说明23](23_时钟校核与断电恢复.md)。不自动配置NTP。
- WATCHDOG默认空，专门验证timeout、nowayout及magic-close后再启用。
- 真实控制需HARDWARE_WRITES=1、对应入口写许可及动作白名单同时满足；独立停止也要允许动作4。
- D2状态3仅指令回读确认。状态5经人工现场核查后，可在客户上位机向原指令/独立停止寄存器写0，或登录网页“人工核查”解除；不能自动复位或重发。上位机负责人员及核查结果留档，网关保留复位来源、时间和原控制审计；存储故障仍拒绝复位。

以仪表1为例：正常周期写30000=0，独立停止周期写30007=0；写的是原指令/请求寄存器，状态30001/30008仍只读。确认现场状态、停止旧报文重试并留档后才操作，读回相应三字为0确认复位成功。网页填写核查人员、结果并勾选确认也可解除所选周期。两条路径均不停止浮子、不补发动作；下一动作由人员另行明确提交。完整客户步骤见[12第8节](12_客户通讯协议V3.md)。

在“历史与诊断→近期事件”检查control_reset（Modbus）或control_maintenance_reset（网页）记录。source是复位来源，reset_time_ms为网关复位时间，before保留被解除周期的完整指令、目标、内部ID、发送标志、结果与计数，after为复位后状态；stop区分正常与独立停止。Modbus记录不包含操作人员或核查结果，这两项查客户上位机日志；网页操作同时保留operator/reason。事件为近期记录，长期资料及时归档；时间未确认时结合时钟诊断核对时间。

### 9.4 允许写控制：按顺序开通

先确认唯一控制方、现场许可、仪表绑定及正常采集，处理旧控制周期，再执行以下步骤：

1. 网页“端口与仪表”选择实际入口：TCP勾选“允许TCP提交命令”；RTU在对应北向口勾选“北向写许可”。
2. 勾选实际核准的动作，独立停止也必须勾选“停止”，点击“保存并应用配置”。
3. 设备终端备份service.env，将HARDWARE_WRITES设为1并核对；WATCHDOG/TLS_CERT/TLS_KEY仍保持空值。
4. 无执行中控制时，网页“系统维护→重启网关程序”或手动重启任选一种；重新登录核对simulate=false、mode=normal、hardware_writes_enabled=true、control_error为空，采集正常后再进行人工控制试验。

~~~sh
# 备份修改前的服务配置，保留现场参数。
cp -p /home/level-gateway/config/service.env "/home/level-gateway/config/service.before-control-$(date -u +%Y%m%dT%H%M%SZ).env"

# 开通真实动作总开关，重启后才生效。
sed -i 's/^HARDWARE_WRITES=.*/HARDWARE_WRITES=1/' /home/level-gateway/config/service.env

# 核对总开关及本轮默认关闭的看门狗、HTTPS参数；缺项或值不符时先用编辑器核对。
grep -E '^(HARDWARE_WRITES|WATCHDOG|TLS_CERT|TLS_KEY)=' /home/level-gateway/config/service.env

# 手动重启应用；已采用网页重启时不再执行此条。
sh /home/level-gateway/current/deploy/service.sh restart
~~~

完整开通、只读核对和关闭步骤见[系统维护26第3～4节](26_系统维护与控制写入操作说明.md)。开通仅允许D2动作/复位，不允许任意改液位计寄存器；0是复位，不是停止。管理员密码不参与Modbus校验。

### 9.5 网页修改密码和程序重启

“系统维护”提供修改密码、程序重启，不提供整机重启。改密码需原密码，两次新密码一致，成功后注销所有会话但不重启采集。程序重启需现场确认；1/2控制拒绝，3/4/5保持，重复提交只安排一次，受理期间拦截新控制/复位及改配置。独立后台任务正常停启核心/网页，失败时报告，不自动循环重试。网页重连后重新登录核对运行时间和采集。

本台Buildroot用新监督脚本启动后自动支持网页程序重启；电脑直接运行和未经适配的systemd模式默认禁用此按钮。默认HTTP、WATCHDOG空值继续保持。系统维护详见[26](26_系统维护与控制写入操作说明.md)。

## 10 升级与回退

### 10.1 共同原则

先协调上位机暂停新控制提交，完成或核查原周期，保存现场配置、日志和当前release。使用相应架构的新精简包，不重新上传文档、客户资料或整个项目。

配置和数据库继续保留；旧库名gateway-v2.db继续使用。升级不换空库，不通过恢复旧库绕过控制锁存。V1/64槽位配置须人工重新分配，不只改版本数字。

新包NORTH_VERSION为3.2（文件标记，不是北向版本寄存器）。迁移schema3后禁止回退到0.3.x；仅同一64槽位/schema3且支持命令11的3.2标记兼容版本允许回退。旧资料JSON或标记3不够证明新版数据库兼容。

网页升级基础版安装后，后续兼容应用包可直接按[说明29](29_网页上传升级操作说明.md)从网页上传。下面手动升级步骤继续保留，首次启用也使用此流程。

### 10.2 本次Buildroot设备升级

从 0.6.0 或 0.7.0 进入 0.8 时，网页方式按说明29使用过渡包；手动方式先按说明33完成本机预授权。已有0.8的正常升级保留config/license.json，不重复收费、不要求联网续期。安装器未通过授权会在停服前退出。

推荐解压新包后，执行第4.0节的`--guided`命令，检测到原配置后进入升级分支。已经有管理员时不重新设置密码。以下仍保留手动升级命令，向导与手动选一种即可。

先按第3、4节上传、解压和校验**实际新包**。以下以0.8.3-20261117-r1为例。升级保留现有账号、端口、数据库和服务配置。升级后按[时钟说明23](23_时钟校核与断电恢复.md)开通并校核一次。

# 检查新核心调度。
/home/level-gateway/current/bin/gateway-core --health-check --ipc unix:/home/level-gateway/data/core.sock

# 检查监督器，继续核对网页、数据及北向读取。
sh /home/level-gateway/current/deploy/service.sh status
~~~

安装器备份数据库到data/gateway.before-新版本.db，配置到config/gateway.before-新版本.json；service.env自动另存为config/service.before-新版本.env，也可按第9节转存电脑。已有release不覆盖。

**0.4.3升级会保留service.env已有参数值，只补齐缺失的支持项。** 例如原文件没有RTC_DEVICE时自动补上/dev/rtc0；原有WEB_LISTEN、ALLOW_CLOCK_SET等值不变。补齐前备份为config/service.before-新版本.env。原0.3.2安装器不补齐缺失参数，不能拿旧脚本代替新脚本。RTC路径仍须现场核对；ALLOW_CLOCK_SET原值为0时不会自动开通，按[说明23](23_时钟校核与断电恢复.md)设置后校时。不要用新模板覆盖旧文件。

健康失败仅允许回退到标记3.2且支持schema3和命令11的兼容64槽位程序，并继续同一控制库；首次从0.3.x升级失败会停留待诊断，不自动恢复旧程序或旧库。

升级保留已有状态5，不会自动解除或重发。安装后确认软件版本为0.8.3、发布标签为0.8.3-20261117-r1，并强制刷新旧网页。按9.3节核对“人工核查”及客户上位机的人工复位流程。本版支持远程液位修改、网页修改密码、程序重启、模拟量采集和按槽位或名称筛选历史。状态5人工核查规则沿用0.3.4。

### 10.3 systemd分支提示

本台不是systemd；本节仅供以后其他固件使用。systemd接管后不能直接运行install.sh或rollback.sh，它们停启的是自身PID监督。

systemd升级须先停web/core，保持原库并用新binary备份，校验包及配置，复制精简文件到新release，原子切换current，再用systemctl启动两服务。使用下方附录的人工流程；不叠加service.sh实例。

### 10.4 回退

只回退已安装、支持64槽位及schema3的兼容应用，不恢复旧数据库。0.3.x不可作为本版回退目标。先确认目标release的摘要及控制语义。

~~~sh
# 指定已由厂家核准且已经安装的64槽位兼容版本；此变量必须按现场实际填写。
gateway_rollback_version=填写已安装的兼容版本标签

# 检查目标摘要、配置后回退应用；不恢复旧库，0.3.x会被拒绝。
sh /home/level-gateway/current/deploy/rollback.sh "$gateway_rollback_version"
~~~

这条命令只适用于service.sh管理。旧完整release可能包含资料；暂留是为回退和校验，确认不再需要后另行清理整个旧release，不擅自删其中部分文件造成SHA失配。

| --- | --- |

## 附录：systemd人工升级

仅供systemd固件，由已核对过服务管理方式的厂家人员执行。本次Buildroot设备跳过本附录。新包已上传解压并确认架构，现场周期已核查；逐条成功才继续。

~~~sh
# 指定实际新包目录，使用前换成已确认标签。
gateway_new_pkg=/tmp/gt6757s-0.8.3-20261117-r1-linux-arm64

# 从已验证包读取release标签，确认与预期一致。
gateway_new_release=$(cat "$gateway_new_pkg/RELEASE")

# 设置新release目标目录。
gateway_new_dest="/home/level-gateway/releases/$gateway_new_release"

# 确认目标尚不存在，非0时停止，不覆盖旧目录。
test ! -e "$gateway_new_dest"

# 核对包内全部摘要。
(cd "$gateway_new_pkg" && sha256sum -c SHA256SUMS)

# 新binary检查现有配置，不启动或迁移源库。
"$gateway_new_pkg/bin/gateway-core" --check-config --config /home/level-gateway/config/gateway.json

# 保存当前旧release路径，回退核对时使用。
gateway_old_dest=$(readlink /home/level-gateway/current)

# 显示旧release路径，记录在本次维护记录中；新终端不会保留上述变量。
printf '%s\n' "$gateway_old_dest"

# 新程序先检查本机已保存授权；失败时停止操作，原服务继续运行。
"$gateway_new_pkg/bin/gateway-core" --check-license --license-file /home/level-gateway/config/license.json

# 停止systemd整个web/core进程组。
systemctl stop level-gateway-web.service level-gateway-core.service

# 确认inactive，再核对没有遗留手动实例。
systemctl status level-gateway-web.service level-gateway-core.service

# 新binary制作一致性升级前备份；目标必须尚不存在。
"$gateway_new_pkg/bin/gateway-core" --db /home/level-gateway/data/gateway-v2.db --backup-db "/home/level-gateway/data/gateway.before-$gateway_new_release.db"

# 保存现场应用配置。
cp /home/level-gateway/config/gateway.json "/home/level-gateway/config/gateway.before-$gateway_new_release.json"

# 保存启动环境设置。
cp /home/level-gateway/config/service.env "/home/level-gateway/config/service.before-$gateway_new_release.env"

# 复制前再确认新release不存在。
test ! -e "$gateway_new_dest"

# 复制完整新release，不运行包内install.sh。
cp -R "$gateway_new_pkg" "$gateway_new_dest"

# 赋予程序与部署脚本执行权限。
chmod 755 "$gateway_new_dest"/bin/* "$gateway_new_dest"/deploy/*.sh "$gateway_new_dest"/deploy/S99levelgateway

# 校验复制后的完整release。
(cd "$gateway_new_dest" && sha256sum -c SHA256SUMS)

# 原子保存schema3配置，保留原32台绑定并追加槽位；前面已做配置备份。
"$gateway_new_dest/bin/gateway-core" --migrate-config --config /home/level-gateway/config/gateway.json

# 检查临时链接无残留；存在时先调查原操作。
test ! -e /home/level-gateway/current.new && test ! -L /home/level-gateway/current.new

# 创建指向新release的临时链接。
ln -s "$gateway_new_dest" /home/level-gateway/current.new

# 原子替换current，需已确认mv支持-T。
mv -Tf /home/level-gateway/current.new /home/level-gateway/current

# 用systemd启动新core及web，不调用service.sh。
systemctl start level-gateway-core.service level-gateway-web.service

# 等待初始启动，之后健康检查。
sleep 3

# 检查新核心调度，失败先查日志并维持控制关闭。
/home/level-gateway/current/bin/gateway-core --health-check --ipc unix:/home/level-gateway/data/core.sock

# 核对systemd状态，再检查网页版本、采集与北向。
systemctl status level-gateway-core.service level-gateway-web.service
~~~

inactive状态下systemctl status可能返回非0，这一步用于查看停止状态；其他命令失败不继续。人工分支没有自动回退。

需回退时先systemctl停止两服务，核对gateway_old_dest中3.2文件标记、摘要及64槽位/schema3兼容性（禁止0.3.x）；按同样链接切换方法指回旧release，再systemctl启动。保留当前库，不恢复升级前数据库。

## 网页复位控制失败与不确定结果（0.4.2）

登录网页，进入“历史与诊断”，展开“控制失败与不确定结果复位”。页面列出全部64个槽位保留的状态4和5，包括未启用槽位及旧版本记录；正常动作与独立停止分别显示。状态4表示控制失败，状态5表示结果不确定，两者不能混为机械故障或已完成。

1. 查看仪表编号、原COM/站址、通道、指令、错误码、结果说明及是否可能已发送。
2. 状态4点击“复位失败结果”；状态5点击“核查并复位”，先核实现场状态。
3. 填写核查人员/工号、现场核查结果与复位原因（至少4字），勾选现场确认。
4. 点击“确认复位（不重发动作）”。成功后选中通道的指令/请求、状态和错误归零，累计次数保留，原记录及复位人员、原因、来源、时间写入审计。另一通道的结果保持。

全程只需要浏览器访问网关，无需连接Modbus TCP。复位不写南向H129或H699，不停止浮子，不自动重发；若需再次动作，须另行明确下发。状态1/2执行中及状态0/3不在本页面提供复位。周期已变更、已复位、未登录、缺少确认或保存失败会拒绝，不能用旧表单清除新的周期。

SYS3会因状态4或5保持常亮；复位所有相关结果且没有其他告警后才熄灭。只清一条记录，不保证消除其他告警。以往页面只筛选状态5，导致状态4虽使SYS3常亮，却显示“当前无需处理”；0.4.2已补齐。

2026-10-27现场连接反馈：网页访问192.168.1.230:8088，Modbus TCP监听192.168.0.230:502。下文原192.168.0.230上传/网页示例须按实际网口、电脑路由及服务监听替换；升级不会自动更改现有监听IP。升级后强制刷新浏览器，核对version=0.7.0，再按本章末尾网页复位步骤处理原状态4/错误2；不会自动清除旧结果。

软件0.4.3仅将测量Ⅲ名称更正为“测量Ⅲ（罐底）”；北向3及南向H699=0x0020保持，7仍为远程密度。升级后强制刷新浏览器核对名称；网页状态4/5复位功能沿用0.4.2，不自动清除原控制或重发动作。

## 12 网络设置与失联恢复

网页“系统维护→网络设置”修改两个网口IP、掩码和最多一个默认网关；TCP监听随所选网口变化，端口和权限保留。新地址人工确认后保存，180秒不确认或试用期间重启则恢复原参数。FUN临时恢复IP和Console步骤见[说明31](31_网络设置与失联恢复.md)。初次安装仍使用已有IP，不自动修改厂家网卡配置；新版网页会在两个IPv4网口监听原端口。

系统/etc/net.conf与/etc/net2.conf、data/network-state.json及data/network-backups属于必要运行配置/恢复数据，须保留。不要在网络试用期间手动安装、重启或切换程序。每次修改前备份原系统网络文件、应用配置及service.env；任务未结束时禁止应用升级。

0.8.3-20261117-r1 允许仪表带故障码下发已开通的操作及独立停止。升级后先人工核查旧控制结果，旧状态4／错误3可复位，再提交新动作。现场验证带故障码时的认证、指令应答和回读，并核对仪表故障字及SYS3继续反映现场状态。
