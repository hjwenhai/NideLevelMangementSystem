## 2 准备物品与电脑连接

### 2.1 准备

GT6757S及匹配电源、电脑、普通网线、可传数据的Type-C USB线、485双绞线、1台已知参数的液位计。需要同时接业务口和维护口时，电脑再加一块USB网卡；测试北向RTU时准备USB-RS485适配器。液位计按自己的要求独立供电，不从网关485端子取电。

设备电源以实物标识和厂商要求为准；本地规格书标注DC9～48V、V+/V-和Earth。Console Type-C用于USB转串口调试，设备仍需正常电源供电。COM3/COM4的485与232复用，使用A/B采集时不要同时接其TX/RX设备。

### 2.2 网口分工与示例IP

以下是隔离调试网的**示例规划**，实际地址先查设备；若已在现场网络运行，沿用现场规划，不能直接照抄改IP。

| 接口 | Linux接口（厂家映射，现场核对） | 示例网关IP/掩码 | 示例电脑IP | 用途 |
| --- | --- | --- | --- | --- |
| ETH1 / Ethernet1 | eth0 | 192.168.1.230 / 255.255.255.0 | 192.168.1.10 | 最终Modbus TCP业务口。 |
| ETH2 / Ethernet2 | eth1 | 192.168.0.230 / 255.255.255.0 | 192.168.0.10 | SSH/SFTP、厂家管理网页。 |
| Console UART Type-C | 电脑识别为一个COM口 | 不涉及IP | 115200、8N1、无流控 | 初次查IP、系统及网络登录失败时调试。不是四个采集COM之一。 |

```text
首次：电脑有线口 ──网线── ETH2（维护口）
      电脑USB    ──数据线── Console UART（推荐保留）
      GT6757S COM1 A/B ──双绞线── 液位计1 A/B

双网口阶段：电脑第二网卡/上位机 ──网线── ETH1（业务口）
```

初次只有一条网线也能安装：先在维护口同时验证网页和TCP读取，验证后在“系统维护→网络设置”把Modbus TCP接入网口切到业务口。两网口不自动互通，不配置网络桥接。平板以后通过兼容的USB网卡，或连接维护网口的外部Wi-Fi接入点访问网页；GT6757S本身不因此具备Wi-Fi。

### 2.3 Windows网卡设置

1. 打开Windows“网络连接”→找到实际连接设备的以太网适配器→属性→IPv4。
2. 假设设备维护口实际为192.168.0.230，电脑设192.168.0.10、掩码255.255.255.0；隔离直连不填默认网关和DNS。
3. 确认该地址没有与其他设备重复；若电脑另一网卡/Wi-Fi也在相同子网，先解决路由冲突。
4. 在电脑PowerShell运行，示例IP替换为实际维护口：

```powershell
ipconfig
ping 192.168.0.230
Test-NetConnection 192.168.0.230 -Port 22
ssh root@192.168.0.230
```

ping通而22端口不通，只表示网络通但SSH未开放，不代表网关应用坏了。首次SSH连接核对设备身份/主机指纹后接受；用户名使用实际账户。不要用关闭电脑全部防火墙的方法代替定位。

## 3 Console登录、SSH和系统探测

### 3.1 Console进入设备

1. 数据线接电脑USB与设备Console UART，安装V1.8资料中的`驱动程序/USB转串口驱动`。
2. Windows设备管理器查看新出现的COM编号，在现有串口终端中选该编号。
3. 配置115200 bps、8数据位、无校验、1停止位、无流控。此配置来自Buildroot手册第9页截图；**与液位计默认4800/8E1不同**。
4. 正常上电后看启动信息，按回车出现登录提示。厂商手册的初始账户为root，初始密码为htnice，仅适用于未改密码的原厂镜像，以实际账户为准；网页管理员密码另行创建。
5. 先执行以下只读命令，将输出保存或发回：

```sh
uname -a
getconf LONG_BIT
cat /etc/os-release
cat /proc/1/comm
ip addr
df -h /home /tmp
ls -l /dev/ttyS1 /dev/ttyS2 /dev/ttyS3 /dev/ttyS4
ls -l /dev/led /dev/led2 /dev/led3
```

个别Buildroot没有getconf/os-release/ip，可分别提供错误信息、`file /bin/sh /bin/busybox`及`ifconfig -a`输出，不要猜系统位数。

若不知道IP，优先从Console读取。厂商资料的FUN长按3秒临时恢复IP功能，只在确认`/etc/reset.conf`未被定制、系统已正常启动后使用；ETH1/2会临时变为1.230/0.230，重启恢复旧值。**不要按住FUN再上电**，那是厂家文件系统更新模式。本次安装应用不刷系统、不重分区。

### 3.2 Buildroot与Ubuntu的SSH分支

| 实际系统 | 厂家资料描述 | 操作分支 |
| --- | --- | --- |
| Buildroot原厂镜像 | SSH已集成、默认未开启；Telnet/FTP通常开启 | 先用Console登录，核对`/etc/init.d/#S50sshd`是否存在、是否已有S50sshd。若符合原厂布局，按下列步骤开启SSH。 |
| Ubuntu原厂镜像 | 预装OpenSSH | 先测试22端口；账户/服务策略以实机为准，有普通账户时用sudo，不假设root网络登录必然允许。 |
| 定制镜像/上述文件不存在 | 无法凭V1.8资料确定 | 发回系统及服务信息后确定方法，不套用另一系统的启动配置。 |

仅当Buildroot存在禁用脚本、未存在启用脚本且确认设备为本次试验机时，设备Console执行：

```sh
ls -l '/etc/init.d/#S50sshd' /etc/init.d/S50sshd
mv '/etc/init.d/#S50sshd' /etc/init.d/S50sshd
reboot
```

重启后再从电脑测试SSH。第一条ls对尚不存在的文件报错不等于需要删除文件；若已有S50sshd，跳过mv，核对服务。不要先关掉唯一还能登录的入口。Telnet/FTP若作为临时备用，仅在隔离调试连接使用，网络登录稳定后按现场要求处理。

### 3.3 选安装包

| 探测结果 | 包 | 是否继续 |
| --- | --- | --- |
| uname=aarch64，用户态确认64位 | linux-arm64 | 推荐匹配实机使用。 |
| uname=armv7l/armv8l，用户态确认32位 | linux-armv7 | 使用32位包。 |
| 内核/用户态不一致、位数未知、工具缺失 | 暂不选 | 发回探测结果；当前安装器按uname检查架构，混合情况须单独核对，不能改ARCH文字绕过。 |

当前0.7.0-20261108-r3的两种架构精简包在电脑项目的`output/packages/`。无需在板端安装Go、Node.js或Python，运行包已包含编译文件。每条命令的详细注释、电脑环境及升级流程见[运行部署维护说明10](10_运行部署与维护.md)。

## 4 电脑准备首次配置和上传

### 4.1 首次单台配置

已提供[首次单台配置示例](附件/config.board-first-1.json)：COM1/COM2南向、COM3/COM4停用；只有编号1、地址1启用；4800/8E1、超时500ms、快速周期3000ms；TCP绑定示例维护IP192.168.0.230:502；所有控制关闭。它只用于新机首次只读测试，不是现场最终配置。

在电脑项目的“设备采集网关”目录操作：

```powershell
New-Item -ItemType Directory -Path output/board-prep -Force
Copy-Item 'docs/附件/config.board-first-1.json' output/board-prep/gateway.first.json
```

用文本编辑器或后续提供的信息修改`gateway.first.json`：`tcp.listen`为实际维护口IP:502，`meters[0].address`为首台实际站址，`ports[0]`串口参数与仪表一致；JSON不加注释、保存UTF-8无BOM。电脑校验：

```powershell
./output/windows-amd64/gateway-core.exe --check-config --config output/board-prep/gateway.first.json
```

应显示`valid config`。失败先修配置，不能上传后强行启动。网关端改波特率不会替液位计改站址或波特率。

## 5 设备安装和首次启动

下列设备命令使用ARM64示例；ARMv7时完整文件名及解压目录都替换为linux-armv7。安装、设备节点和502端口的首次试验使用root权限；非root账户先通过sudo取得本次需要的权限。

### 5.1 先探测、校验，再安装

```sh
cd /tmp
sha256sum gt6757s-0.7.0-20261108-r3-linux-arm64.tar.gz
tar -xzf gt6757s-0.7.0-20261108-r3-linux-arm64.tar.gz -C /tmp
# 核对精简包内全部必要文件；本包不包含probe.sh。
(cd /tmp/gt6757s-0.7.0-20261108-r3-linux-arm64 && sha256sum -c SHA256SUMS)
```

设备包摘要与电脑相同；精简运行包不包含probe.sh；系统环境按第3节设备命令记录，不需另部署诊断脚本。检查`sha256sum/readlink/setsid/stty/tar`等工具，额外确认`mv --help`有`-T`，/home空间足够、设备节点存在。确认已有程序是否占tty或SYS灯，记录相关进程，不能杀不明服务。

```sh
sh /tmp/gt6757s-0.7.0-20261108-r3-linux-arm64/deploy/install.sh /tmp/gt6757s-0.7.0-20261108-r3-linux-arm64
```

新机首次缺少管理员时，安装器只安装、不启动，显示初始化提示，这是预期行为。目录为`/home/level-gateway`：bin在current/bin，配置在config，数据库和账号在data，日志在logs。如果目录/同名release已存在，不能反复执行安装去覆盖，按第11节查看。

### 5.2 只在全新安装替换首次配置

确认没有原应用数据库、没有已启动服务、安装器刚生成初始模板后执行：

```sh
cp /home/level-gateway/config/gateway.json /home/level-gateway/config/gateway.installed-default.json
cp /tmp/gateway.first.json /home/level-gateway/config/gateway.json
/home/level-gateway/current/bin/gateway-core --check-config --config /home/level-gateway/config/gateway.json
```

已有应用/数据库时跳过此替换，不能拿单台样例覆盖现场配置。初始模板是64台而非1台，所以新机必须先做本节或等价配置再采集，否则没有接线的63台会制造超时与告警。

用设备编辑器修改`/home/level-gateway/config/service.env`。首次示例值如下；WEB_LISTEN必须换为设备已有维护口IP，不能仅修改应用监听就当成修改系统IP：

```ini
WEB_LISTEN=192.168.0.230:8088
HARDWARE_WRITES=0
ALLOW_CLOCK_SET=0
RTC_DEVICE=/dev/rtc0
WATCHDOG=
TLS_CERT=
TLS_KEY=
LEDS=0
```

先LEDS=0，待第8节确认灯节点和占用再改1。真实控制、校时和看门狗先不启用；尚无有效校时记录时会有时间警告，数据有效性仍可按valid判断。此文件是shell配置，等号两边不留空格，保存Linux换行；不用粘贴本机密码。

### 5.3 创建网页管理员

新机先按[说明10第5节](10_运行部署与维护.md#5-创建管理员并启动)分步创建管理员：关闭回显、单独运行初始化命令、输入12～128个ASCII字符密码并回车、恢复回显，再确认文件。程序没有密码提示语，运行后光标停住表示等密码；不要将后续查询/启动命令或空行一起粘贴。

成功显示“管理员凭据已初始化”。系统root密码与网页管理员密码分别管理。已有管理员文件不删除重建；终端输入未显示时执行带注释的恢复命令：

## 6 四个485口配置和接线

### 6.1 端子与角色

| 物理口 | 厂家Linux节点 | 接液位计时选什么 | 说明 |
| --- | --- | --- | --- |
| COM1 | /dev/ttyS1 | 南向采集 | 使用COM1的A/B。 |
| COM2 | /dev/ttyS2 | 南向采集 | 使用COM2的A/B。 |
| COM3 | /dev/ttyS3 | 南向采集或北向RTU或停用 | A/B是485；同口TX/RX为复用232，不能同时接。 |
| COM4 | /dev/ttyS4 | 南向采集或北向RTU或停用 | 同上；作为北向时不能再挂液位计。 |

上述节点须实机核对，当前程序使用厂家此映射。四口角色都可配置，并不限于COM3/4可做北向。USB调试Console不占这四口。

先断开本次试验总线的其他主站/采集软件，一条南向总线只由此网关轮询。网关A/B按液位计实际端子定义接线；不同厂家的A/B、D+/D-标识不一定同义，未知时发端子照片核对，不把485接到232 TX/RX。屏蔽、参考地、终端电阻与偏置按双方接线要求及现场线长确定，不能把四个隔离口的地任意并在一起，也不能每台都加终端电阻。

### 6.2 网页操作

1. 登录维护网页→“端口与仪表”。首次确认COM1/COM2=南向，COM3/COM4=停用；本版正常模式至少2路南向，只给COM1配置一台，COM2空口无仪表轮询。
2. COM1波特率设成仪表实际值；FW-9000默认4800、偶校验E、1停止位，数据位固定8。超时先500ms，后续按实测调整。
3. 编号1选择COM1、实际站址、启用，填名称；只启用真实已接线的仪表。温度/密度详情先保留样例设置；若仪表不支持，记录型号/异常再决定关闭对应详情。
4. 快速周期3000ms、详情30000ms、模式“正常采集”。保持“允许TCP提交命令”和所有动作未勾选，北向写许可关闭。
5. “保存并应用配置”，看到成功后回“当前数据”。同一总线的站址必须不同，范围1～243；不同COM可同址。仪表编号与站址是两个概念。
6. 每口最多16台，总槽位64。删除/改绑/重排前导出配置；任一正常/停止周期非空闲时，所有配置变更会被拒绝，要先按D2流程处理周期。

| 最终配置例 | COM1 | COM2 | COM3 | COM4 | 最大液位计数 |
| --- | --- | --- | --- | --- | --- |
| 32台＋北向RTU | 南向16 | 南向16 | 北向RTU | 停用 | 32 |
| 48台＋北向RTU | 南向16 | 南向16 | 南向16 | 北向RTU | 48 |
| 64台 | 南向16 | 南向16 | 南向16 | 南向16 | 64，仅TCP |

槽位1～8/9～16/17～24/25～32分别对应COM1～4只是推荐分配；程序允许重新绑定。首次用同一台仪表轮换四个COM时，编号1可以跟随测试口，不必改成9/17/25。

## 7 液位计采集和北向读取测试

### 7.1 COM1单台通过判据

仪表自身显示正常后，在网页观察至少5分钟：液位与仪表显示按分辨率吻合；数据年龄周期性下降；`valid & 0x0001 != 0`表示液位有效；支持温度/密度的仪表按各自有效位比较。静止液位数值不变是正常的，更新应看年龄或采集组序号，不能仅看值变化。

数据的valid=127只表示七项数据在有效窗口，不能证明无故障；故障字须`valid & 0x0020 != 0`后判断其值。quality的时间未确认bit7可与有效数据并存；不要把它误判为接线失败。

电脑运行该工具需要Python3，先检查`python --version`；若没有，改用已有Python3的完整程序路径或现有Modbus调试软件。电脑项目目录运行标准库TCP工具；IP/端口/Unit ID使用实际首次配置，以下均为**零基地址**：

```powershell
python tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 read 2 2
python tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 read 28 2
python tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 summary --meters 1
python tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 read 1000 24
python tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 status --slot 1
```

| 检查 | 预期 | 中文说明 |
| --- | --- | --- |
| 地址2起2字（FC04） | [3,64] | 北向版本3、容量64；不表示64台已启用。 |
| 地址28起2字（FC04） | [3,12] | D2能力和每台控制块步长；不表示已开通真实写权限。 |
| 编号1摘要1000起24字 | valid、液位、质量、COM/站址正确 | summary命令自动换算；原始读取高字在前。 |
| 控制status（FC03） | 正常/停止状态0、指令0、错误0 | 首次没有提交控制时应空闲；仅查询不动作。 |

任意编号n的摘要地址`1000+24×(n-1)`。若用自己的Modbus调试软件，设置TCP Server实际IP、502、Unit ID1、FC04；注意软件可能把零基1000显示成31001，必须确认其偏移设置，不能再盲目加1。

### 7.2 用一台仪表逐个验四口

1. COM1通过后，保存当前读数、配置及日志。
2. 在网页暂时取消编号1启用并保存，待采集停止后移动485接线。
3. 将下一口设南向；编号1绑定下一口并重新启用，保持实际站址不变，保存。正常模式始终至少2路南向，已测空口可保留南向但不启用任何仪表；不能把南向只留1路。
4. COM2、COM3、COM4分别重复单台5分钟，记录A/B、TX/RX灯、读数、年龄和错误。
5. 同一时刻只启用实际接线的一个绑定。完成四口后按最终规划恢复，不用把同一台仪表重复配置为四台。

### 7.3 掉线与恢复

只读试验状态下，断开本台485通讯线而保留仪表供电，记录时刻：应出现采集告警；距每项最后一次成功采集**超过9000ms**后对应valid位清0，旧原值可保留但不能当当前测量显示。不是要求断线瞬间清0。重新接回后应自行恢复，记录恢复时间；无需重启或删除数据库。

有多口/多台后再断一台或一路，观察其余口持续更新。掉线仪表会增加该总线超时，需记录其余同口仪表延迟，不能只看在线总数。

### 7.4 采集周期实测记录

默认3000ms是快速组调度目标，9000ms是有效窗口，网页每2秒刷新不是仪表采集周期。编号1的三组元数据FC04地址3064起36字，顺序液位/温度状态/密度状态，每组12字；组内偏移2～3为成功序号、8～9为年龄ms。其他编号n起址`3000+144×(n-1)+64`。

电脑记录约1分钟样本，不会向仪表写入：

```powershell
1..60 | ForEach-Object {
  Get-Date -Format o
  python tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 read 3064 36
  python tools/modbus_client.py --host 192.168.0.230 --port 502 --unit 1 summary --meters 1
  Start-Sleep -Seconds 1
} | Tee-Object -FilePath output/board-prep/COM1-single-read.log
```

循环实际间隔还包括请求耗时，不是精确1秒。成功组序号变化的观测时间差用于估计刷新，年龄样本用于统计P50/P95/max；约1秒采样不能证明毫秒级延迟。概要序号会因任意采集组成功递增，不能直接算完整快速轮询周期。先单台，再每口2台、8台、16台、最终32/48/64台各至少30分钟，随后72小时；将完整日志交给我们分析实际指标。

### 7.5 双网口与可选北向RTU

双网口测试：核对ETH1实际IP，在“系统维护→网络设置”选择实际业务网口并试用、确认，随后到“端口与仪表”复制只读访问地址（示例192.168.1.230:502）；0.7.0网页在两个IPv4网口监听8088。电脑业务网卡192.168.1.10或上位机接ETH1，维护网卡保持ETH2，重复上方读取命令但改host为业务IP。两边同时正常后记录端口和IP。只改监听不改Linux网卡IP；修改系统IP按说明31完成网页试用、确认与恢复验收，并保留Console。

北向RTU测试：留一口为“北向RTU”，移除该口所有启用液位计绑定，用USB-RS485接该口A/B。上位机串口设网关北向站号1、38400/8E1（可按现场另设），FC04读2起2字、1000起24字；FC03读30000起12字，不能用FC04读控制区。南向4800和北向38400是不同总线参数，不需相同。RTU与TCP应读到同一编号缓存；两次读取时刻不同可有更新，不要求逐字永久一致。64台配置无法同时保留北向RTU。

## 8 指示灯检查

### 8.1 先确认硬件节点和占灯服务

默认厂商节点SYS1=/dev/led、SYS2=/dev/led2、SYS3=/dev/led3。记录原厂哪些服务在写灯；只处理已确认的灯驱动方，不用killall。停止本应用并确认core/web已停止后，且厂商灯控制也已协调，单独做硬件开关测试。节点必须真实存在且为字符设备，避免重定向意外创建普通文件。

```sh
sh /home/level-gateway/current/deploy/service.sh stop
ls -l /dev/led /dev/led2 /dev/led3
for node in /dev/led /dev/led2 /dev/led3; do
  [ -c "$node" ] || { echo "Missing LED character device: $node"; exit 1; }
done
printf '1' > /dev/led
sleep 1
printf '0' > /dev/led
printf '1' > /dev/led2
sleep 1
printf '0' > /dev/led2
printf '1' > /dev/led3
sleep 1
printf '0' > /dev/led3
```

观察每次是否只有相应SYS灯亮灭，记录或录像。失败先发节点/驱动/占用信息，不认为软件逻辑显示正确就等于硬件可用。完成后service.env设`LEDS=1`并启动应用。

### 8.2 运行灯态

| 场景 | SYS1 | SYS2 | SYS3 | 如何判定 |
| --- | --- | --- | --- | --- |
| 正常采集、全部快速项有效、时间暂未确认 | 每秒心跳，亮/灭各0.5秒 | 常亮 | 慢闪，亮/灭各1秒 | 首次尚无校时记录时的正常时间警告。 |
| 部分仪表快速采集正常、部分异常 | 心跳 | 慢闪2秒周期 | 警告慢闪，严重故障可能常亮 | 须至少有一台全快速项正常。 |
| 有启用仪表，但没有一台全快速项正常 | 心跳 | 快闪0.5秒周期 | 警告或严重故障 | 与“启用零台”区别。 |
| 无启用仪表或维护模式 | 心跳（调度健康时） | 灭 | 按时间及其他告警 | 不把灭灯误认成采集软件停止。 |
| 仪表故障/控制失败或未知/存储或驱动异常 | 心跳；调度失活时SYS1常亮 | 按采集状况 | 常亮 | 查看诊断和日志；普通掉线不必然构成严重故障。 |
| 全正常且时间可信 | 心跳 | 常亮 | 灭 | 网页校时保存RTC，开机检查通过后自动确认，不通过开关强行消除告警。 |

电脑可FC04读22起5字，依次三灯模式、驱动启用、驱动错误。模式0灭/1常亮/2慢闪/3快闪/4心跳；LEDS=1时应启用=1、错误=0。比对网页“历史与诊断”与肉眼灯态。TX1/RX1～TX4/RX4为收发灯，短帧闪烁不一定肉眼清晰；有TX没有RX优先查接线/站址/串口参数，不能单凭灯下结论。

## 10 通过手动试运行后设置开机自启

只启用一种服务管理方式。保存现场配置和日志后，按PID1及实际固件分支执行；不要在手动监督仍运行时再启动systemd实例。

| 系统 | 分支 | 通过判据 |
| --- | --- | --- |
| Buildroot，实际支持/etc/init.d/S* | 确认同名文件不存在，将current/deploy/S99levelgateway复制到/etc/init.d/S99levelgateway，chmod755 | 重启后仅一套core/web监督进程，网页/TCP/采集恢复。 |
| Ubuntu，PID1=systemd | 先停止手动service.sh；使用下方两个systemd单元 | 不安装Buildroot的S99作为唯一启动保障。 |
| 厂家cron自启/定制init | 先提供实际bootset/crontab/PID1 | 依据实机选方式；不能重复加多个入口。 |

Buildroot分支设备命令，仅在确认目录机制及同名目标不存在后执行：

```sh
cp /home/level-gateway/current/deploy/S99levelgateway /etc/init.d/S99levelgateway
chmod 755 /etc/init.d/S99levelgateway
```

Ubuntu/systemd分支：先`sh /home/level-gateway/current/deploy/service.sh stop`，创建以下两个文件；首次仍以root权限运行，之后专用账户及权限另行安排。

`/etc/systemd/system/level-gateway-core.service`：

```ini
[Unit]
Description=Level gateway core
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/home/level-gateway
ExecStart=/bin/sh /home/level-gateway/current/deploy/supervise.sh core
Restart=on-failure
RestartSec=3
KillMode=control-group
TimeoutStopSec=40

[Install]
WantedBy=multi-user.target
```

`/etc/systemd/system/level-gateway-web.service`：

```ini
[Unit]
Description=Level gateway web
Requires=level-gateway-core.service
After=level-gateway-core.service network-online.target

[Service]
Type=simple
WorkingDirectory=/home/level-gateway
ExecStart=/bin/sh /home/level-gateway/current/deploy/supervise.sh web
Restart=on-failure
RestartSec=3
KillMode=control-group
TimeoutStopSec=40

[Install]
WantedBy=multi-user.target
```

```sh
systemctl daemon-reload
systemctl enable --now level-gateway-core.service level-gateway-web.service
systemctl status level-gateway-core.service level-gateway-web.service
```

**systemd接管后不要再用service.sh start/restart/install.sh升级**：当前安装器停启的是自身PID监督，不能识别systemd监督。此分支升级须先用systemctl停止两服务、保持配置和库、一致性备份、人工按新release校验并切换，再systemctl启动；本轮不直接运行安装器做systemd升级，后续据实机补部署自动化。服务状态用systemctl；应用日志仍在/home/level-gateway/logs。systemd文件为待实机验证示例。

重启验证前导出配置、记录软件版本/boot标识；重启后重复单台读取，核对端口角色、站址、日志和只有一个采集主站。不要在未决动作期间把重启当作复位。

## 11 常见问题定位和停止方法

| 现象 | 先查什么 | 操作边界 |
| --- | --- | --- |
| ping不通 | 电源/网线/实际网口IP/电脑掩码及路由；Console读取ip | 不通过猜地址和刷系统解决。 |
| ping通、SSH不通 | 22端口、Buildroot SSH禁用状态、账户权限 | 先走第3节，网页8088不是SSH。 |
| `Exec format error` | 包架构及内核/用户态位数 | 发probe，不改ARCH或乱换系统。 |
| install提示release exists | 已安装版本、current及原库/配置 | 不覆盖同名release、不删原数据库；此时按已有安装处理。 |
| 出现`\r`/`not found`、bad interpreter | 是否用了早期未修正包或编辑器把LF改成CRLF | 用完整现行0.7.0-20261108-r3包重新校验，不修改已发布包后忽略摘要失败。 |
| 页面打不开 | WEB_LISTEN是否127.0.0.1、是否绑定设备实际IP、web.log、8088端口 | 应用监听与Linux网卡IP分开。 |
| TCP连不上 | 502监听IP、tcp.enabled、Unit ID、端口占用、业务口接线 | 临时维护口测试与最终业务口测试使用不同host。 |
| 有采集发送但无有效数据 | A/B定义、站址、4800/8E1、485/232复用、其他主站、设备日志 | 不先打开动作写入试图“修复通讯”。 |
| 页面显示32启用但只接1台 | 是否仍用安装默认32模板 | 新机按首次单台配置；已有现场配置不直接覆盖。 |
| 时间警告/SYS3慢闪 | 网页clock诊断、RTC及校时记录 | 按说明23校核并复测，不用开关强行设可信。 |
| SYS硬件与网页不一致 | 节点、LEDS、驱动错误、厂商占灯进程 | 不杀不明服务，不创建假/dev/led文件。 |
| 保存配置被拒 | 是否存在非空闲正常/停止周期 | 查D2锁存，未知先厂家现场核查，不删库解锁。 |
| 参数区不能写 | 本版普通参数写未实现 | 客户简易控制不是任意寄存器透传。 |

手动监督/Buildroot方式停止、重启：

```sh
sh /home/level-gateway/current/deploy/service.sh stop
sh /home/level-gateway/current/deploy/service.sh start
```

systemd方式停止/重启使用systemctl，不混用。任何情况下保持`data/gateway-v2.db`及配置；不能只复制正在运行的.db而遗漏WAL，需要数据库备份时使用本程序`--backup-db`，见[10部署维护](10_运行部署与维护.md)。

## 网页复位控制失败与不确定结果（0.4.2）

登录网页，进入“历史与诊断”，展开“控制失败与不确定结果复位”。页面列出全部64个槽位保留的状态4和5，包括未启用槽位及旧版本记录；正常动作与独立停止分别显示。状态4表示控制失败，状态5表示结果不确定，两者不能混为机械故障或已完成。

1. 查看仪表编号、原COM/站址、通道、指令、错误码、结果说明及是否可能已发送。
2. 状态4点击“复位失败结果”；状态5点击“核查并复位”，先核实现场状态。
3. 填写核查人员/工号、现场核查结果与复位原因（至少4字），勾选现场确认。
4. 点击“确认复位（不重发动作）”。成功后选中通道的指令/请求、状态和错误归零，累计次数保留，原记录及复位人员、原因、来源、时间写入审计。另一通道的结果保持。

全程只需要浏览器访问网关，无需连接Modbus TCP。复位不写南向H129或H699，不停止浮子，不自动重发；若需再次动作，须另行明确下发。状态1/2执行中及状态0/3不在本页面提供复位。周期已变更、已复位、未登录、缺少确认或保存失败会拒绝，不能用旧表单清除新的周期。

SYS3会因状态4或5保持常亮；复位所有相关结果且没有其他告警后才熄灭。只清一条记录，不保证消除其他告警。以往页面只筛选状态5，导致状态4虽使SYS3常亮，却显示“当前无需处理”；0.4.2已补齐。
